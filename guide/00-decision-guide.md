# 트래픽 규모별 의사결정 가이드

> **목적:** 트래픽과 데이터 규모에 따라 어떤 기술이 필요한지 판단 기준 정리

---

## RPS별 단계 가이드

### Phase 1: 1 ~ 100 RPS (MVP)

**적정 기술:**
- 단일 Spring Boot 인스턴스
- 단일 MySQL
- 기본 Connection Pool (10개 정도)

**해야 할 것:**
- 기본 인덱스 설정
- 쿼리 가독성 유지

**굳이 안 해도 되는 것:**
- Redis, Kafka, MSA 도입
- 복잡한 캐싱 전략

**이유:** 트래픽이 낮을 때는 단순함이 곧 안정성

---

### Phase 2: 100 ~ 500 RPS (성장 초기)

**해결해야 할 문제:**
- 느린 쿼리가 눈에 띄기 시작
- DB Connection 대기 발생

**도입 검토:**
1. **MySQL Slow Query Log 분석**
2. **인덱스 추가/조정**
3. **HikariCP 튜닝** (max-pool-size 20~30)
4. **쿼리 N+1 제거** (`@EntityGraph`, fetch join)

**아직 이른 것:**
- Redis (단순 인덱스로 해결되는 경우 많음)
- 비동기화

---

### Phase 3: 500 ~ 2,000 RPS (성장기)

**해결해야 할 문제:**
- 인덱스로도 한계
- DB CPU 사용률 증가
- 외부 API 호출이 응답 시간에 영향

**도입 검토:**
1. **Redis 캐시** (조회 위주 데이터)
2. **비동기 처리** (`@Async` 또는 이벤트)
3. **Read Replica** (읽기 부하 분산)
4. **APM 도구 도입** (Pinpoint, Zipkin)

**아직 이른 것:**
- MSA 분리 (모놀리식으로도 충분)
- Kafka (단순 비동기는 @Async로 충분)

---

### Phase 4: 2,000 ~ 10,000 RPS (확장기)

**해결해야 할 문제:**
- 단일 인스턴스 한계
- 캐시로도 부족한 부하
- 비동기 작업의 신뢰성 요구 증가

**도입 검토:**
1. **수평 확장** (Load Balancer + 다중 인스턴스)
2. **Stateless 설계** (Session을 Redis로)
3. **Kafka 도입** (신뢰성 있는 비동기)
4. **Connection Pool 최적화** (DB Proxy 검토)
5. **CDN** (정적 자원)

---

### Phase 5: 10,000+ RPS (대규모)

**해결해야 할 문제:**
- 단일 DB 한계
- 도메인 간 결합도

**도입 검토:**
1. **MSA 분리** (도메인별)
2. **DB 샤딩**
3. **이벤트 기반 아키텍처** (CQRS, Event Sourcing)
4. **Service Mesh** (Istio 등)

---

## 데이터 규모별 가이드

### 1만 건 이하
- 인덱스 효과 미미
- Full Scan으로도 충분히 빠름
- 굳이 최적화 불필요

### 1만 ~ 10만 건
- 인덱스 필수
- 기본 페이지네이션
- 쿼리 튜닝

### 10만 ~ 100만 건
- 복합 인덱스 설계
- 커서 기반 페이지네이션
- 캐싱 도입 검토

### 100만 ~ 1,000만 건
- 파티셔닝 검토
- Read Replica 분리
- 검색은 Elasticsearch 검토

### 1,000만 건 이상
- 샤딩
- 별도 검색 엔진 필수
- 콜드 데이터 분리 (아카이빙)

## 상황별 가이드

### 외부 API 호출이 있을 때

```
외부 API가 응답 시간에 미치는 영향
├─ 무관 (사용자 응답 후 처리해도 됨) → 비동기화
├─ 부분 영향 (실패해도 OK) → Circuit Breaker
└─ 핵심 의존성 (실패하면 안 됨) → 동기 + 재시도 + Timeout
```

### 트래픽 패턴이 불규칙할 때

```
피크 시간이 평소의 N배
├─ 2~3배 → 인스턴스 미리 증설
├─ 5~10배 → Auto Scaling (HPA)
└─ 100배+ → 큐 기반 부하 분산 (Kafka 등)
```

### 데이터 정합성이 중요할 때

```
정합성 요구 수준
├─ 강한 정합성 → 단일 트랜잭션 또는 분산 락
├─ 결과적 일관성 OK → Outbox Pattern, 이벤트 기반
└─ 캐시 정합성 → TTL + 이벤트 기반 무효화
```

## 안티 패턴 (하지 말 것)

### 1. 트래픽 없는데 MSA부터 도입
- 운영 복잡도만 증가
- 분산 트랜잭션 문제 발생
- 처음엔 모놀리식이 정답

### 2. 측정 없이 캐시 도입
- 변경 빈도 높은 데이터에 캐시
- 무효화 비용이 더 큼
- 정합성 문제만 추가

### 3. 모든 작업을 비동기로
- 디버깅 어려워짐
- 순서 보장 안 됨
- 트랜잭션 경계 모호

### 4. Pool size를 무조건 키우기
- DB가 포화되면 오히려 악화
- 메모리 사용량 증가
- 측정으로 결정해야 함

---

## 핵심 원칙

1. **측정 후 도입** - 추측이 아닌 데이터로 결정
2. **단순함 유지** - 필요할 때까지 도입하지 않기
3. **트레이드오프 인식** - 모든 기술에는 비용이 있음
4. **점진적 진화** - 한 번에 다 바꾸지 않기
