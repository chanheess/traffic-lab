# 시나리오 5 - 평소 저트래픽, 피크 시 급증 패턴

> **카테고리:** 트래픽 패턴 대응
> **학습 목표:** 평상시 비용 최소화 + 피크 시 안정성 확보의 균형 전략

---

## 상황 설명

소규모 판매 사이트
- **평소:** 시간당 수십 명 방문 (1 RPS 미만)
- **피크 (이벤트):** 300명이 30분간 동시 집중 (수십~100 RPS 추정)
- **하루 종일 피크는 1~2시간만 발생**
- 이벤트 외 시간엔 거의 트래픽 없음

이런 상황에서 "전체 API 합산 트래픽" 까지 고려하면 피크 시 의외로 부하가 클 수 있습니다.

---

## 핵심 문제

| 문제 | 설명 |
|---|---|
| 평소 비용 낭비 | 피크에 맞춰 서버 키워두면 99% 시간이 낭비 |
| 피크 시 다운 | 평소에 맞춰 서버 작게 두면 이벤트 시 다운 |
| 단일 페이지 ≠ 단일 요청 | 페이지 1개 로드 시 API 5~10개 호출, 실제 RPS는 표면 RPS의 5~10배 |

---

## 실제 RPS 추정 (단순 계산)

### 표면적 계산
- 300명 × 30분 → 분당 10명 → **약 0.17 RPS**
- "별거 아니네" 라고 생각할 수 있음

### 실제 계산 (페이지당 API 호출 고려)
- 사용자 1명 페이지 진입 시:
  - 상품 목록 조회 API
  - 상품 상세 API
  - 재고 확인 API
  - 사용자 정보 API
  - 장바구니 API
  - 추천 상품 API
  - = **약 6~10개 API 호출**

- 300명이 30분간 평균 5페이지 탐색 시:
  - 300명 × 5페이지 × 8 API = 12,000 API 호출
  - 12,000 / (30분 × 60초) = **약 7 RPS**

- 이벤트 시작 직후 1분간 100명 동시 진입 시:
  - 100명 × 8 API = 800 API 호출
  - 800 / 60초 = **약 13 RPS**
  - 피크 1초당으로 따지면 **순간 30~50 RPS**

### 결론
표면 RPS는 낮아 보여도 **실제 API RPS는 10배 이상** 될 수 있습니다.

## 의사결정 가이드

```
평소 저트래픽 + 피크 시 급증 패턴
├─ 피크 차이 10배 이내 → 과(여유) 프로비저닝 + 캐시
├─ 10~50배 → Auto Scaling + 정적 자원 CDN
├─ 50~100배 → 사전 예약 스케일업 + 큐 기반 부하 분산
└─ 100배+ → 트래픽 분리 (이벤트 페이지 별도 인스턴스)
```

## 박찬희님 케이스 (300명 집중) 권장 전략

### 1순위: 캐시 (가성비 최고)

이벤트 페이지는 보통 같은 데이터를 반복 조회

```java
@Cacheable(value = "eventInfo", key = "#eventId")
public EventInfo getEventInfo(Long eventId) {
    return eventRepository.findById(eventId);
}
```

**효과:**
- 300명이 같은 이벤트 페이지 진입해도 DB 조회는 1번만
- Redis 메모리 비용 거의 0

---

### 2순위: 정적 자원 CDN

이벤트 페이지의 이미지, CSS, JS는 CDN으로 분리

```
사용자 → CDN (이미지, CSS) ← 빠름
사용자 → 서버 (API만) ← 부하 줄어듦
```

**효과:**
- 서버 트래픽 50~70% 감소
- 무료 CDN (Cloudflare 등) 활용 가능

---

### 3순위: 적정 규모 + Auto Scaling

평소엔 작은 서버 1대, 피크 시 자동 증설

| 시점 | 인스턴스 |
|---|---|
| 평소 (23시간) | t3.micro 1대 |
| 피크 (1시간) | t3.small 2~3대 |

**비용 예시 (AWS 기준 월 환산):**
- 평소 + 피크 모두 t3.small 3대 상시: 약 7만원/월
- Auto Scaling 적용: 약 1.5만원/월
- **약 78% 절감**

---

### 4순위: 사전 예약 스케일업

이벤트 시작 시간이 정해져 있다면 미리 키워두기

```yaml
# Kubernetes HPA 또는 cron 기반 스케일링
schedule: "0 19 * * MON"  # 매주 월요일 오후 7시
action: scale-up
replicas: 3
```

**왜 사전 예약?**
- Auto Scaling은 트래픽 감지 후 증설 (지연 발생)
- 이벤트 시작 직후 폭주를 미리 방지

---

### 5순위: 큐 기반 부하 분산 (선착순 이벤트만 해당)

선착순 100명 이벤트처럼 동시 진입이 폭발적인 경우

```
사용자 → 대기열 페이지 → 순차 처리 → 실제 이벤트 페이지
```

**적용 사례:**
- 인터파크 티켓팅
- 무신사 한정판 발매
- 야놀자 특가

**박찬희님 케이스:** 300명 규모면 굳이 필요 없음

---

## 하지 말아야 할 것

### 1. 평상시 트래픽에 맞춰 서버 작게 두기
- 이벤트 시 다운되면 신규 사용자 영구 이탈
- 가장 흔한 안티 패턴

### 2. 피크에 맞춰 상시 큰 서버
- 99% 시간이 비용 낭비
- 스타트업이라면 치명적

### 3. Kafka, MSA 도입
- 이 규모에서 절대 불필요
- 운영 복잡도만 증가
- 모놀리식 + 캐시 + Auto Scaling이 정답

## 측정으로 검증할 것

이벤트 직전, 직후로 다음을 측정해야 합니다.

| 지표 | 측정 방법 | 임계값 |
|---|---|---|
| 응답 시간 p95 | APM 또는 Actuator | 500ms 이하 |
| DB 커넥션 사용률 | HikariCP 메트릭 | 80% 이하 |
| Redis Hit Ratio | Redis INFO | 95% 이상 |
| 에러율 | 로그 분석 | 0.1% 이하 |
| CPU/메모리 | 모니터링 도구 | 70% 이하 |

## 비용 효율 관점

300명 집중 트래픽은 **개인 개발자도 무료 또는 저비용으로 충분히 처리 가능**합니다.

### 추천 구성 (AWS 프리티어 또는 저비용)
```
- EC2 t3.small (피크 시 2~3대로 Auto Scaling)
- RDS t3.micro (단일 인스턴스)
- ElastiCache (Redis) t3.micro
- CloudFront (정적 자원)
- 예상 월 비용: 3~5만원
```

### 또는 더 저렴하게
```
- Cloudflare (무료 CDN + 무료 Caching)
- Vercel/Netlify (정적 페이지 무료)
- Supabase 또는 Firebase (백엔드 일부 위탁)
- 예상 월 비용: 1만원 이하
```

## 면접 답변 포인트

**Q: "300명 정도 몰리는 이벤트는 어떻게 처리하시겠어요?"**

> "표면적인 RPS만 보면 작아 보이지만 페이지당 API 호출이 5~10개라 실제 백엔드 RPS는 30~50까지 올라갈 수 있습니다.
>
> 이 규모에서 가장 효과적인 건 화려한 분산 시스템이 아니라 캐시와 CDN입니다. 이벤트 정보는 Redis에 캐시해 DB 조회를 1회로 줄이고, 이미지 같은 정적 자원은 CDN으로 분리해 서버 부하를 70% 가까이 낮출 수 있습니다.
>
> 그 위에 Auto Scaling이나 이벤트 시작 전 사전 예약 스케일업으로 안정성을 확보하면, 평상시엔 작은 서버 1대로 운영하면서 피크 1시간만 증설하는 구조로 비용도 1/5 수준으로 줄일 수 있습니다.
>
> Kafka나 MSA를 도입할 규모는 절대 아니고, 모놀리식 + 캐시 + 정적 자원 분리만으로 충분합니다."

## 핵심 메시지

**작은 서비스의 트래픽 대응은 "어떤 기술을 도입하느냐"가 아니라 "어디서 부하를 줄이느냐"의 문제입니다.**

- DB로 가는 요청을 줄여라 → **캐시**
- 서버로 가는 요청을 줄여라 → **CDN**
- 평소엔 작게, 피크엔 크게 → **Auto Scaling**

이 3가지가 작은 서비스의 정답입니다.
